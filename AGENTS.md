# AGENTS.md

Working guide for AI coding agents and humans in this repository. It is grounded in the
source and configuration as of **2026-11-03**. `README.md` is the project overview, but it is
not authoritative: it has drifted from the code in several places. Where they disagree, the
code, `package.xml`, `pixi.toml`, and the tests win. The known drift is listed at the end.

## 1. What this project is

A connectome-constrained simulation of the *Drosophila* male central nervous system (FLYCNS)
flying an X3 multirotor in Gazebo through ROS 2, with a mission layer that searches a forest
for a person.

There are two layers, joined by one message:

- **Brain / pilot** (`src/fly_brain`, `src/fly_drone`): reads sensors, runs the fly model,
  and produces body-frame velocity. It owns flying, obstacle avoidance, and the escape
  reflex. `fly_brain` has **no ROS dependency** and is testable offline. `fly_drone` is the
  ROS 2 adapter around it.
- **Mission layer** (`mcp-server/`): an MCP server with five tools. It plans a coverage path,
  sends the brain one world-position goal at a time, and runs the person detector over the
  downward camera. **It never commands velocity.**

```
MCP client
   | MCP
   v
mission layer -- Goal JSON, /fly_brain/goal --> brain --> Twist --> drone_controller
   ^                                                               --> Gazebo / vehicle
   '--- odometry, downward camera, GoalStatus -----------------------'

brain <-- forward camera, 3-D lidar, odometry
```

A goal is an explicit instruction to fly, and the brain's output is armed when one arrives
(`arm_on_goal`). With no goal and no arming, nothing moves.

## 3. Setup and commands

### Environment

The project uses **pixi** (verified with pixi 0.84.0). It provides ROS 2 Lyrical, Gazebo,
OpenCV, FastAPI/FastMCP, brian2, and the build tools. Use `pixi run` for project commands;
do not assume the system Python or a system ROS installation.

```bash
pixi install
pixi run colcon build --symlink-install
source install/setup.bash        # zsh: source install/setup.zsh
```

`pixi.toml` has an empty `[tasks]` section: there is no `pixi run test` or `pixi run build`.
Use the explicit commands below, or the `Makefile`: every target runs through
`pixi run bash`, so `make build`, `make brain` and `make demo-search` work from any shell on
Linux or macOS without `pixi shell` first.

`FLYCNS` is **not vendored**. The `mock` backend works without it. For the real network:

```bash
git clone https://github.com/IONOFIELD/FLYCNS.git ../FLYCNS
cd ../FLYCNS && python scripts/make_testdata.py && cd -
```

The toy graph (912 neurons) is generated by `make_testdata.py`. The real MaleCNS graph needs
a neuPrint token and `scripts/setup.py` in the FLYCNS clone.

### Run the simulation

```bash
# Gazebo + bridges + drone_controller. The vehicle is armed and hovers; no brain output.
pixi run bash -c 'source install/setup.bash && ros2 launch fly_bringup sim_launch.py'

# The full stack: sim_launch + brain_pilot. Mock brain; output disarmed until a goal.
pixi run bash -c 'source install/setup.bash && ros2 launch fly_bringup brain_launch.py'

# FLYCNS toy connectome, with a sphere thrown at the drone every 20 s.
pixi run bash -c 'source install/setup.bash && ros2 launch fly_bringup brain_launch.py \
    backend:=flycns threats:=true'

# Headless / CI. The cameras and lidar still render off-screen; video is off.
pixi run bash -c 'source install/setup.bash && ros2 launch fly_bringup brain_launch.py \
    headless:=true video_recording:=false'
```

`brain_launch.py` takes `backend:=mock|flycns`, `flycns_repo:=PATH`, `flycns_data:=testdata`,
`enable_output`, `arm_on_goal`, `threats`, `threat_period_s` (0 means only on request),
`threat_delay_s`, `threat_distance_m`, `threat_speed_mps`, `use_sim_time`, plus the
pass-through arguments `gazebo_simulation`, `headless`, `camera_tracking`,
`camera_tracking_target`, `video_recording`, and `video_dir`. Worlds available under
`worlds/` are `forest_search`, `cave_rescue`, and `collapsed_building`; the mission defaults,
tests, keep-outs, and measured results are written for `forest_search`.

`drone_controller` is not optional in the simulation. It arms the X3 and republishes the
latest body-frame twist at 20 Hz. The world spawns the vehicle about 2.5 m above the floor;
without this node it falls onto a slope, and the brain's commands reach nothing.

### Run the MCP server

```bash
# stdio, for an MCP client
pixi run python mcp-server/mcp_server.py

# HTTP on 127.0.0.1:8799
pixi run python mcp-server/mcp_server.py --http 8799

# Brain in-process over a flat kinematic world: no Gazebo, no ROS
MISSION_LINK=sim pixi run python mcp-server/mcp_server.py
```

Important: `MISSION_LINK` defaults to `auto`, which selects `ros` whenever `rclpy` imports.
Inside the pixi environment `rclpy` **does** import, even if no Gazebo or brain node is
running. Set `MISSION_LINK=sim` explicitly when you want the in-process world.

`MUSE_API_KEY` (or `MODEL_API_KEY`) enables Muse. Without it, `PERSON_DETECTOR=auto` silently
falls back to the colour blob, and `mission_status.detector` says `color:... (stand-in, not a
vision model)`. Read that field before believing a sighting.

## 4. Architecture

### 4.1 Brain and pilot

```
forward camera --detect.py--> Boxes --+
3-D lidar -----lidar.py-----> Threats +--> LoomTracker --> Percept
odometry --------------------------------> altitude/attitude
                                              |
                                              v
                                         encoders.encode
                                              |
                                              v
                                    brain.step (mock | flycns)
                                              |
                                              v
                          MotorLayer.decide(percept, spikes, state)
                                              |
                                              v
                                   safety clamp -> Bridge.send
```

- `fly_brain` must stay importable without `rclpy`. It uses pydantic for schemas that cross
  the ROS/MCP boundary and dataclasses for internal settings and parameter bundles.
- `Controller` is a process-wide singleton with a reentrant lock. The ROS node, FastAPI
  worker threads, and the MCP process all go through it. Do not create a second controller
  for convenience; tests use `reset_controller()`.
- `Controller.ensure_brain()` builds the network lazily. There are no FastAPI startup/lifespan
  events anywhere, deliberately.
- The `mock` backend is a rate stand-in, not a connectome. Its giant-fibre threshold
  (`MOCK_GF_THRESHOLD_HZ = 7.0`) is deliberately tied to the encoder's output scale. If you
  change the loom gate, gain, or peak rate, update the mock and its comment or the two
  backends stop predicting each other.
- The `flycns` backend loads a graph from `FLYDRONE_REPO` / `FLYDRONE_DATA`, resolves exact
  cell-type names from `circuit.json`, and replaces stimulated types with Poisson sources.
  Stimulated types therefore cannot be read back. `monitor_types=()` is intentional: adding
  voltage monitors costs memory and is not used for the control loop.
- `steer` and `forward` in `circuit.json` are **empty**. The pursuit decoder is not wired.
  Do not claim pursuit control works; `PursuitParams` and the `PURSUE` branch exist, but they
  have no calibrated output channels.

The behaviour priority is strict:

```
ESCAPE > COOLDOWN > AVOID > NAVIGATE > PURSUE > HOLD
```

- `ESCAPE` is triggered by a giant-fibre (`DNp01`) or TTMn spike. A spike is an **event**, not
  a rate: one trigger commits to a fixed manoeuvre for `hold_ms` (350 ms), then decays for
  `decay_ms` (250 ms), then a refractory `cooldown_ms` (800 ms).
- The escape runs away from the threat bearing and 35° up, at 3 m/s base speed; extra GF
  spikes scale it, and PSI adds 25%. Above 40° elevation it dives instead of climbing.
- `AVOID` is the graded side-step for a loom that is at least 12° in size and growing at
  least 3°/s but did not fire the GF.
- `NAVIGATE` is the mission layer's only path into the brain. It converts a world-frame
  `Goal` into body-frame velocity with a saturated P controller. Three rules matter:
  climb first when well below the goal, face the direction of travel, and latch arrival.
  With a goal set, HOLD/AVOID hold the goal altitude, not the 3 m pursuit cruise altitude.
- `_clamp()` is the last stop for every command. It enforces `MAX_SPEED` (5 m/s),
  `MAX_CLIMB` (2 m/s), `MAX_YAW` (2 rad/s), and the `MIN_ALTITUDE_M` (1 m) floor. Never
  bypass it.

### 4.2 Perception and the reflex

- Both the forward camera and the 3-D lidar end in a `fly_brain.perception.Threat`: bearing,
  elevation, angular size, and range when available. The brain does not know which sensor saw
  the object.
- `LoomTracker` differentiates angular size **per `(source, track_id)`**. It needs at least
  three samples before differentiating; the first frames of a track are where merges and new
  ids look like a size leap. It reports the most urgent object: smallest optical
  time-to-contact `size / expansion` among growing objects, else the largest.
- An object growing more slowly than `max_tau_s` (3 s) from contact is scenery: expansion is
  reported as zero. A lidar threat with `moving=False` is also scenery.
- Encoder rates are small on purpose. `FLYDRONE_PEAK_HZ` defaults to 5.0, the FLYCNS anchor;
  `FLYDRONE_LOOM_GAIN` defaults to 16; `FLYDRONE_LOOM_MIN_DPS` defaults to 3.0. Above the
  gate, both `loom_speed` (LC4, expansion) and `loom_size` (LPLC2, size) are driven; below it
  neither is, even for a large object.
- The forward camera detector (`fly_drone/detect.py`) defaults to colour mode with magenta
  (`FLYDRONE_DETECT_COLOR`), deliberately unlike anything in the forest world. `motion` mode
  exists but smears when the camera moves; only use it roughly station-keeping.
- The brain's lidar is the 3-D `lidar_3d` (32 planes, ±30° elevation, 320 beams per plane,
  10 Hz), not the single-plane lidar. `lidar.py` places returns in the world using odometry
  attitude, drops returns more than 2 m below or 4 m above the airframe, clusters on a polar
  grid, freezes a track's physical width after it settles, and only calls a track moving when
  its world-frame centroid moves consistently. This is what prevents ground sweeps, cluster
  breathing, and static trees from firing the reflex.

### 4.3 ROS side

`brain_pilot` (`fly_drone/node.py`) subscribes to:

- `/drone/odometry` (`nav_msgs/Odometry`)
- `/drone/camera_image` (`sensor_msgs/Image`) and `/drone/camera_info` (`CameraInfo`)
- `/drone/lidar3d_pointcloud` (`sensor_msgs/PointCloud2`) unless `FLYDRONE_LIDAR=0`
- `/fly_brain/goal` (`std_msgs/String`, JSON `Goal`)

It publishes `/fly_brain/goal_status` and `/fly_brain/telemetry` every tick. It runs one brain
tick on a timer at `LOOP_HZ` (20 Hz), not in the image callback; only the newest frame is
kept, because a tick costs tens of milliseconds and queuing frames would back up the executor.
Everything perceptual is stamped with the node clock, so under `use_sim_time` the control
period and escape timing follow Gazebo's clock.

`brain_pilot` publishes velocity on `/drone/drone_motion` through the configured bridge
(default `TwistBridge`). It also publishes `true` on `/drone/enable` while armed; it never
publishes `false`, because Gazebo's `MulticopterVelocityControl` cuts the rotors on `false`.
A stop is a zero twist, which is a hover.

`drone_controller` is a separate node in the `drone` namespace. It:

- subscribes to `drone_motion`, `odometry`, `camera_image`, `camera_info`, and
  `lidar_pointcloud` (the single-plane lidar, for the teammate's sensor-fusion messages);
- publishes `cmd_vel` (bridged to Gazebo), `position`, `raw_sensor_data`, and `sensor_fusion`;
- publishes `true` on `enable` once the Gazebo subscribers connect;
- republishes the latest `drone_motion` twist at 20 Hz.

Do not remove or rename it. The brain never talks to Gazebo directly.

### 4.4 Mission layer

`mcp-server/mcp_server.py` wraps the FastAPI app in `app/main.py` with
`FastMCP.from_fastapi`. Every route's `operation_id` is the MCP tool name. `/health` is
excluded from the tool list. There is exactly one prompt, `find_person`.

| Tool | What it does |
|---|---|
| `search_for_person` | Plans coverage, flies it, detects people, confirms a positive from above, ends hovering over the person. |
| `scout_area` | Flies the same coverage but keeps every sighting and finishes the whole area; optional `return_home`. |
| `mission_status` | State, progress, position, brain goal, sightings, log. `best.estimated_xy` is the position to report. |
| `abort_mission` | Stops the runner and leaves a station-keeping goal at the current position. Safe at any time. |
| `look_for_person` | Runs the detector once on the newest downward frame without moving. |

Both flight tools take `area` (box or polygon in world metres), `altitude_m`, `speed_mps`,
`lane_overlap`, `sweep_heading_deg`, `keepouts`, `min_confidence`, `confirm_detections`, and
`dry_run`. `scout_area` adds `return_home`. `dry_run` is the cheap way to inspect a plan.

Mission flow:

1. `MissionService.start()` refuses a second mission while one is planned/running. It builds
   the link and detector eagerly, plans, and starts `MissionRunner` on a daemon thread.
2. The runner sends one `Goal` per waypoint, waits for a `GoalStatus` whose goal id matches
   and whose `reached` is true, and re-sends if the brain has not acknowledged (the first
   message to a late-starting node is lost). A leg timeout is
   `max(MISSION_LEG_TIMEOUT_MIN_S, leg_length / speed * MISSION_LEG_TIMEOUT_FACTOR)`.
   Three consecutive timeouts fail the mission.
3. Along the path, every `sample_fraction` of the along-track camera footprint (default 0.5)
   it takes the newest downward frame and calls the detector. The colour stand-in and Muse
   both return a `Detection`; detector failures are returned as `Detection.error`, never
   raised, so one failed API call does not stop a flight.
4. A positive in `search` mode is confirmed by flying to its estimated ground position and
   looking straight down again up to three times. If confirmed, the mission ends in `found`
   with a goal labelled `over person`. In `scout` mode positives are merged (within 6 m) and
   coverage continues.
5. Completion, abort, and failure all end with a `Goal` at the current position (or at the
   start position with `return_home`), so the brain never ends a mission goal-less (which
   would drop it to the low pursuit cruise altitude).

Planner details:

- Boustrophedon cellular decomposition. The sweep line crosses the area; a cell boundary is
  placed where the number of free intervals changes. Cells are toured nearest-first.
- Lane spacing is the downward camera footprint at the flight level, less `lane_overlap`
  (default 0.2). Lower altitude means a smaller footprint, more lanes, and a longer flight.
- Transits between cells are routed around keep-outs with a visibility graph.
- `coverage_estimate` is computed by rasterising the free area against the lane footprints.
  Do not report it as a guarantee; it is still an estimate.
- Keep-outs only matter if `top_z_m + keepout_vertical_clearance_m >= altitude_m`. At the
  default 15 m, none of the fixtures in `mission/keepouts.json` block, so the drone flies
  straight lanes above them. Trees are not keep-outs; unexpected obstacles are the brain's
  reflexes' problem.

Camera and detector details:

- Downward camera defaults: 80° horizontal FOV, 640×480. Image top is the drone's forward,
  image right is the drone's right. `camera.py` assumes flat ground; the forest has about
  6 m of relief, so a bbox-derived position is good to a few metres, and the confirm pass is
  what refines it.
- `MUSE_BASE_URL` defaults to `https://api.meta.ai/v1`; the detector POSTs to
  `/chat/completions` with the JPEG as an `image_url` part and a JSON schema. It retries
  transient failures and drops unsupported extra request fields on a 400. Parsing is
  defensive: strict JSON first, then the first `{...}` block, then an unambiguous prose
  "yes" as a low-confidence detection.
- `PERSON_DETECTOR`: `muse`, `color`, `none`, or `auto`. `auto` chooses Muse only if
  `MUSE_API_KEY` or `MODEL_API_KEY` is set, else colour.
- The mission colour detector defaults to `DETECT_COLOR=blue` (the Gazebo person's jeans).
  This is separate from the forward camera's `FLYDRONE_DETECT_COLOR=magenta`. Do not mix
  them up.

## 6. Conventions and invariants

### Frames and units

- **World:** ENU. `x` east, `y` north, `z` up. The map is 120 × 120 m centred on the origin.
  The forest floor spans roughly −2.5..+3 m, so a flight level is a **world z**, not a height
  above ground. `Goal.z` is world z.
- **Body:** FLU. `x` forward, `y` left, `z` up.
- **Yaw rate:** rad/s, positive is **left** (counter-clockwise from above).
- **Bearing:** `bearing_deg` is positive to the **right** of the nose. A target at +30° needs
  a negative yaw rate to centre it.
- **Pitch:** positive is nose **down** (right-hand rule about the left-pointing body y axis).
  This is the opposite of the aerospace convention; the docstrings say so.
- **Downward camera:** image top is forward, image right is the drone's right.
- Angles in schemas are named with units (`_deg`, `_rad`, `_dps`); distances are metres.
  Keep that naming.

### Safety and control boundaries

- Every command goes through `MotorLayer._clamp()`. Do not add a bypass.
- The mission layer only sends `Goal`s. It must never publish a `Twist` or a velocity.
- A goal arms the brain output (`arm_on_goal`), because a goal is an order to fly. A goal
  also makes HOLD/AVOID hold the goal altitude.
- `/drone/enable` is `true` only; never publish `false` from the brain or controller. A
  `false` cuts the rotors. Stop with a zero twist.
- `drone_controller` arms the vehicle as soon as Gazebo subscribers connect. Keep it running
  in the simulation.
- The safety envelope is `MAX_SPEED=5`, `MAX_CLIMB=2`, `MAX_YAW=2`, `MIN_ALTITUDE_M=1`.

### Code boundaries

- `fly_brain` has no ROS imports. Keep it that way so the MCP server and unit tests can run
  without ROS.
- The mission layer must remain importable without ROS. `RosLink` imports `rclpy` lazily;
  `app/bootstrap.py` adds only `src/fly_brain` to `sys.path`, never `src/fly_drone`.
- `fly_drone` is the ROS adapter; it can import `fly_brain` and `rclpy`.
- Do not add FastAPI startup/lifespan hooks. `FastMCP.from_fastapi` drives the app through an
  in-process ASGI transport and never runs them; links and detectors are built on first use.
- Keep `MissionService` single-flight. `start()` raises if a mission is already planned or
  running; callers must `abort_mission` first.

### Style

- Python uses `from __future__ import annotations`, type hints on public functions, dataclasses
  for settings/parameter bundles, and pydantic models for schemas that cross the MCP/ROS
  boundary.
- The code intentionally carries explanatory comments with measured numbers and reasons.
  Preserve that style; when you change a threshold or a behaviour, update the explanation,
  not just the constant.
- Keep telemetry/logging bounded. `Mission._log` is an 80-entry deque and status returns the
  last 15 lines; do not turn it into an unbounded list. The brain publishes telemetry every
  tick, so do not add expensive serialization there.
- Do not add dependencies casually. ROS dependencies belong in the relevant `package.xml`;
  Python/environment dependencies belong in `pixi.toml`, and pixi updates `pixi.lock`. Do not
  hand-edit the lock file.
- Prefer editing existing modules over creating parallel abstractions. `fly_brain`,
  `fly_drone`, and `mission` already separate the concerns.

## 8. Testing guidance

There are three useful levels of verification:

1. **Offline unit/component tests** (fast, no ROS):
   `test_perception.py`, `test_encoders.py`, `test_lidar.py`, `test_threats.py`.
   They cover tracking, the loom gate, lidar clustering/ground masking/width freezing, and
   launcher geometry. Run these for any change to perception, encoders, lidar, or threats.
2. **In-process mission tests** (fast, no Gazebo/Muse key):
   `mcp-server/tests`. They run the real planner, real `MotorLayer` navigation, real runner,
   real camera model, and the FastMCP surface against `SimLink`. Run the whole folder for
   changes to planning, runner, mission schemas, MCP routes, navigation, or the mission config.
   Run individual files (`test_coverage.py`, `test_navigate.py`, `test_mission.py`,
   `test_smoke.py`) while iterating.
3. **Live Gazebo tests** (slow, manual):
   `tools/flight_test.py` and `tools/search_test.py` against a running launch. These prove
   sensor rates, the reaction, and the full ROS/Gazebo path. They are not part of the automated
   suite and should not be claimed as run unless they were.

What the automated tests do **not** cover: ROS topic wiring in a live launch, Gazebo physics,
the Muse API call itself, PX4/MAVROS, or the real MaleCNS connectome. Treat README/REFLEX
Gazebo measurements as historical results, not as things the test suite reproduces.

The ament lint tests are in `src/fly_brain/test` and `src/fly_drone/test`. They are useful when
changing package metadata or style, but they are not part of the quick loop. Do not "fix" a
failing functional test by weakening it or skipping it; fix the behaviour.

When changing the MCP surface, update `mcp-server/tests/test_smoke.py`'s `EXPECTED_TOOLS` and
assertions in the same change. When changing a does-everything tool, keep its body schema a
plain `BaseModel` with a default instance so FastMCP flattens it into named arguments; the
smoke test explicitly asserts that there is no opaque `req` property.

## 9. Traps, all of them load-bearing

1. **Import Brian2 on the main thread.** It installs a SIGINT handler at import, which Python
   only permits on the main thread. FastAPI, MCP, and ROS handlers run on worker threads.
   Entry points that can load the FLYCNS backend call `preimport_flycns()` before any
   worker-thread tick. The MCP process needs it with an in-process link (`MISSION_LINK=sim`,
   or `auto` when rclpy is unavailable) and the `flycns` backend.
2. **Never name a setting `FLYCNS_*`.** See above: FLYCNS interprets it as a model
   perturbation.
3. **No FastAPI startup events.** `FastMCP.from_fastapi` never runs the app's lifespan. The
   brain link and detector are built lazily on first use. Do not move that work into startup.
4. **`MISSION_LINK=auto` usually means ROS inside pixi.** `rclpy` imports, so `auto` selects
   `ros` even with no brain running. Use `MISSION_LINK=sim` for the standalone demo/tests.
5. **An unpowered X3 falls.** The world spawns it about 2.5 m above the floor. `drone_controller`
   arms it immediately so it hovers. Without that node it drops onto a slope, and a tilted
   lidar sees the hillside move. Keep `sim_launch.py`'s nodes running.
6. **`/drone/enable=false` cuts the rotors.** The brain and controller publish only `true`.
   A stop is a zero twist. Do not add a "disable" path that publishes `false` while airborne.
7. **Simulation time vs wall clock.** `brain_pilot` runs with `use_sim_time`; its control
   period, expansion rates, and escape hold/decay/cooldown follow Gazebo's clock. The mission
   runner's timeouts and polling are wall-clock. Do not mix them.
8. **Flat ground in geolocation.** A bbox is projected onto `MISSION_GROUND_Z_M`; the terrain
   has ~6 m of relief, so expect a few metres of error and let the confirm pass refine it.
   Report `best.estimated_xy`, not a hand-computed guess.
9. **The lidar must not believe the ground or a breathing cluster.** `lidar.py` uses odometry
   attitude, a vertical band, frozen widths, and a motion gate. A single-plane lidar is blind
   in cruise once the nose drops; do not replace the 3-D path with the single-plane topic.
10. **MockBrain thresholds are tied to the encoder.** If you change `LOOM_MIN_DPS`, the loom
    gain, or `PEAK_HZ`, update `MOCK_GF_THRESHOLD_HZ` / `MOCK_GF_DOUBLE_HZ` and the related
    tests, or the mock and the connectome stop agreeing.
11. **FastMCP body flattening.** The tool bodies must stay plain models with default
    instances. `SearchRequest` / `ScoutRequest` are written that way on purpose. A union such
    as `Model | None` collapses the schema and breaks `call_tool(name, {})`.
12. **Do not import `fly_drone` from the mission layer.** It needs `rclpy` and would make the
    MCP server ROS-only. `app/bootstrap.py` adds only `src/fly_brain` for a reason.
13. **`fly_brain` stays ROS-free.** Do not add `rclpy`, `cv_bridge`, or ROS message imports to
    that package. The offline tests and the in-process link depend on it.
14. **`brake`/`stop` semantics.** `Controller.stop()` disarms, clears the goal, resets the
    motor layer, and sends a zero command. It does not publish `/drone/enable=false`.
15. **`steer` and `forward` are empty in `circuit.json`.** Pursuit is not calibrated. The
    status/README may mention it as future work; do not present it as working.
16. **`REFLEX.md`'s calibration section is aspirational.** It names `brain_status`,
    `get_motor_config`, `test_reflex`, `update_motor_config`, and a `calibrate_reflex` prompt.
    Those are not in the current five-tool MCP surface. Do not build instructions or tests
    that assume they exist.
17. **README's lidar description is stale.** See the drift table below. Use
    `/drone/lidar3d_pointcloud` for the brain; `/drone/lidar_pointcloud` is the single-plane
    lidar used by `drone_controller`'s sensor fusion.
18. **The Makefile is zsh-specific.** `SHELL := /bin/zsh` and `source install/setup.zsh`.
    On a bash-only machine, use the explicit `pixi run bash -c 'source install/setup.bash && ...'`
    commands instead.
19. **Do not run bare `pytest src/` for a quick check.** It collects the ament lint suites as
    well as the unit tests. Use the four named files, or the `mcp-server/tests` folder.
20. **One mission at a time.** `MissionService.start()` refuses a second mission while one is
    active. Abort first; abort also leaves a station-keeping goal.

- **Muse thinks against `max_tokens`.** `muse-spark-1.3` is a reasoning model: its thinking
  tokens count toward the completion budget, and a one-line prompt spends about 190 of them
  (measured 2026-11-03). With a small budget the answer comes back as `content: null` with
  `finish_reason: length`. The detector asks for 1500 and the dodge advisor for 1200, and
  both report an empty answer as an error rather than as "nobody there".

## 11. Known drift, gaps, and stale docs

### README vs code

| README says | Code says |
|---|---|
| The brain uses a 360° **single-plane** lidar on `/drone/lidar_pointcloud`. | The brain uses the 3-D `lidar_3d` (32 planes, ±30°, 320 beams) on `/drone/lidar3d_pointcloud`. The single-plane sensor remains for `drone_controller`'s sensor fusion. |
| `record_video:=false` turns recording off. | The launch argument is `video_recording:=false` (`sim_launch.py` and `brain_launch.py`). |
| The forward camera covers 60 × 47°. | The node reads the real HFOV from `camera_info`; `CAMERA_HFOV_DEG=60` is only a fallback. |
| `src/fly_interfaces/` is "the teammate's sensor-fusion messages". | Correct for `fly_interfaces` (three used messages), but `src/fly_msgs/` also exists as an empty placeholder package. Do not confuse the two. |
| Five MCP tools, `find_person` prompt. | Correct, and asserted by `test_smoke.py`. |
| Gazebo/search results and "working" status table. | Those are historical measurements. The automated suite covers offline and in-process sim, not live Gazebo. Re-run before citing. |
| `pixi run colcon build --symlink-install`. | Correct; `make build` runs plain `colcon build`. Either is fine. |

Separately, `node.py`'s docstring says the pilot can be armed with an `enable_output` MCP
tool. No such tool exists. Arm with the `enable_output` launch/ROS parameter, or send a goal
(`arm_on_goal`).

### REFLEX.md vs current surface

`REFLEX.md` is a valuable design note, but its "Calibrating it yourself" section names MCP
tools and a prompt (`brain_status`, `get_motor_config`, `test_reflex`,
`update_motor_config`, `calibrate_reflex`) that are not implemented in this MCP server. Do not
assume them. Its measured numbers are from the FLYCNS **toy** graph (912 neurons), with the
giant-fibre input hand-wired; the real MaleCNS graph has not been measured here.

### Current gaps

- **Pursuit decoder:** not wired. `circuit.json`'s `steer`/`forward` type lists are empty;
  `PursuitParams` gains default to 0, so pursuit would not move the drone meaningfully.
- **Real connectome:** not vendored and not exercised. The toy graph is what the launch
  defaults to; the real graph needs a neuPrint token and `scripts/setup.py`.
- **PX4 / MAVROS:** adapters exist in `bridge.py` but are not exercised. `px4` needs
  `px4_msgs`, which is not in `pixi.toml`, and raises an explanatory `RuntimeError` if
  selected. `mavros` only needs `geometry_msgs`, but there is no running MAVROS and the adapter
  is untested.
- **Muse:** verified live on 2026-11-03 with a key in a gitignored `.env`
  (`export MUSE_API_KEY=...`, then `source .env`): on the downward frame from 15 m it answers
  "A person lying on the ground between trees", confidence 0.9, box on the figure, ~5 s per
  call. The colour stand-in is what the automated mission tests use; `test_detector.py`
  covers the Muse client against a fake server.
- **Live Gazebo / ROS integration:** not covered by the automated tests. Use the harnesses.
  Flown on 2026-11-03 with Muse: `search_for_person` from the spawn point over
  (-14,-50)..(18,-26) at 15 m ended FOUND at (1.9, -36.2) vs a true (2, -38) in 62 s with 7
  Muse calls and no errors. The Muse dodge advisor answers in 9-20+ s, so it only decides for
  slow or distant objects; every fast sphere's dodge came from the geometry.
- **Other worlds:** `cave_rescue.world` and `collapsed_building.world` exist, but the mission
  defaults, keep-outs, tests, and measured search results target `forest_search.world`.
  `person_target` appears only in the forest world.
- **`fly_msgs`:** placeholder package, no messages.
- **Build and install artifacts:** `build/` and `install/` are generated; don't inspect them
  for source truth.

## 12. Definition of done

Before finishing a change:

- [ ] The relevant offline tests and/or `mcp-server/tests` pass. Do not claim live Gazebo
      verification unless you actually ran it.
- [ ] New behaviour has a test at the same level as the behaviour (unit for perception/
      encoding, in-process mission for planning/flow, smoke for MCP surface).
- [ ] No command bypasses `_clamp()`, and no mission-layer code publishes velocity.
- [ ] `fly_brain` still imports without ROS; the MCP server still imports without ROS.
- [ ] Any changed topic name is updated in `fly_brain/config.py`, `bridge.yaml`, and the
      mission side's shared settings.
- [ ] Any changed MCP tool set updates `EXPECTED_TOOLS` in `test_smoke.py`.
- [ ] Any changed default or measured claim is reflected in the code/docstring, and
      `REFLEX.md`/README are only updated with numbers you actually measured.
- [ ] No generated files (`build/`, `install/`, `log/`, `dist/`, `.pixi/`) are edited or
      committed.
- [ ] The five-tool/one-prompt MCP surface remains intact unless the change explicitly adds
      or removes a tool.
